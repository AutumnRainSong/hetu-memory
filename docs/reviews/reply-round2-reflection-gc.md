# 关于后台反思与边衰减 GC 协商的回复

感谢这轮协商——"基础设施任务与智能增强任务分离"这个原则把我们在 v1.0 里混在一起谈的"后台"彻底解开了，它已经是架构文档的正式原则（v1.2 已落盘）。以下按你提出的六个问题逐一给出技术评估，其中有两条我会给出与你倾向不完全相同的建议，理由和代价都写在明处。

---

## 一、六个问题的技术评估

### 1. 反思默认关闭后，Hot Path 能否独立保证 MVP 记忆质量？哪些长期信息会遗漏？

**结论：能保证"正确性"，会遗漏"整合性"，但 MVP 阶段可接受。**

Hot Path（写入闸门 + 会话内四操作决策）能保证：单条记忆的原子化、去重、冲突检测、正确归属和正确召回——这些是正确性根基，关闭反思不受影响。

会遗漏的是三类跨会话整合信息：

- **跨会话模式**（如"用户连续三次在周五提出部署需求"）——单会话窗口看不到，只有跨会话反思能归纳；
- **延迟显形的关系**（两条记忆在写入时无共现，多次召回后才显出关联）——没有反思通道就没有补建边的时机；
- **陈旧语义的清理**（被 supersede 链掩盖的过时概括）。

**缓解措施已内建于设计**：RAW 层 7-30 天 TTL 给了反思未来开启时的"回看窗口"——RAW 原始事件不删除，反思即使晚开启也能补提炼，不会永久丢失。这正是 RAW 层存在的意义之一。

### 2. 是否设计低成本的会话结束摘要机制？——是，且我建议把它划入基础设施而非智能增强

这是本轮协商我认为最重要的补充。**Session Digest（会话结束摘要）**：

- **触发**：会话结束（进程退出/超时/显式结束信号），单次执行、单会话范围、有界输入输出
- **成本**：无 LLM 依赖也能跑（规则式抽取：实体、时间、意图、原始片段索引）；可选轻量 LLM 提质
- **它解决什么**：反思关闭后，RAW→情节层的提炼通道依然存在（RAW 到期摘要内联的生成来源就是它），**"长期信息遗漏"的最大头被堵上了**
- **它不是什么**：不做跨会话归纳、不做冲突发现、不改写任何已有记忆——那些是反思的职责

建议归属：划入 **Data Maintenance 基础设施任务，MVP 默认开启**。理由：它是"数据正确性"的一部分（RAW 到期内联依赖它），且成本有界、可测试、失败可重放。

### 3. Top-K 满额：拒绝新增 vs 确定性淘汰？

**我的推荐：确定性淘汰（方案 B），MVP 就采用。**

- **拒绝新增的隐性代价被低估**：它让图谱结构被"写入顺序"锁死——早期噪声边永久占位，三个月后真实的高价值关联永远进不来。对一个设计目标是"长期运行、可演进"的记忆系统，这是慢性中毒。
- **淘汰的代价是可控的**：MVP 权重 = 共现次数 × 时间近因的确定性函数（无衰减、无 LLM），比较逻辑是一个纯函数，单测覆盖充分；并列规则取 created_at 较旧者淘汰（时间早的边已证明自己长期未被强化，先让位）。
- **并发一致性**：满额判定与淘汰在同一 Writer 队列内串行执行（我们已决定 MVP 就上统一 Writer 队列），不存在并发比较的竞态。
- **风险声明**：淘汰是"静默信息丢失"的一种形态——被淘汰边的共现事实不再可从图谱恢复（RAW 层仍有原始记录，P2 反思开启后可重建）。这需要在面板上可见（淘汰计数进可观测指标），不做静默。

### 4. 四类边是否分立数量上限？

**是，且已细化**：

| 边类型 | 容量约束 | 理由 |
|---|---|---|
| 共现边 | top-K（默认 32，可配）+ 确定性淘汰 | 高频自动生成，必须限流 |
| 显式 Link | **独立存量上限（默认每节点 ≤ 20，可配）** | 你指出的"限流不控存量"是真实漏洞——rate limit 只管写入速率，不管历史堆积；link 有独立淘汰规则（权重最低者出，link 不参与共现淘汰排序） |
| Supersede 边 | 只受链长上限约束（不按时间失效、不参与 top-K） | 版本历史是正确性数据，衰减/淘汰都无权触碰 |
| Annotation 边 | 不设数量上限 | 数量由 per-agent 注解行为决定且体量小；宿主 PURGED 时联动清理 |

一个补充原则：**满额淘汰只在同类型边内部进行**——共现边满额不能挤掉 link 边，反之亦然。跨类型的容量彼此独立。

### 5. 反思与边衰减同时开启的冲突？

**原则：提案动节点，衰减动边，未决提案冻结衰减，衰减永不触碰结构性边。**

- 反思的产出永远是 **supersede 提案**（动节点内容，经宿主确认流）；它不直接改任何边的权重
- 边衰减只作用于 **共现边与 link 边的权重**；supersede 边与 annotation 边永不衰减（结构性/私有性数据，时间无关）
- **互锁规则**：某节点存在未决合并提案时，该节点的全部边衰减暂停——因为提案被接受后边的去留会重算，先衰减等于基于过期状态做决策
- **执行互斥**：两类任务经同一任务注册表登记，节点级单写者锁（接口本轮预留），保证同一节点同一时刻只有一类任务在动

### 6. 对 OMXF 的影响？

四处需要同步，我已列入 v0.2 修订清单：

1. **Session Digest 来源标记**：节点 provenance 增加 `origin: session-digest | hot-path | reflection`，导入端据此判断该节点的可信级别与是否可参与"独立来源"计数（digest 不计入独立来源，与 RAW 摘要同规则）
2. **边容量元数据**：导出保留边的 `type` 与 `weight`，导入端重建 top-K/link 上限时按同规则执行淘汰——保证 round-trip 后图结构收敛到一致状态
3. **反思提案状态**：P2 后提案节点（pending proposal）导出时标记 `state: proposal`，导入端不自动执行，落为待审
4. **任务状态与一致性**：导入过程视为单次批处理任务，走 Writer 队列；导入中的幂等键 = (owner_id, node_id, content_hash)，防旧快照覆盖新状态（这同时回应你 P0-6 的"仅按 ID 去重"问题）

## 二、对你的最终决策表的确认与一处保留

| 项目 | 确认 |

| 手动后台反思保留 | ✅ 确认（MVP 即可用，正好作为反思效果的验证通道） |
| 定时反思保留接口 | ✅ 确认 |
| 基础设施任务不受开关影响 | ✅ 确认，且新增 Session Digest 归入此列 |
| 共现边 Top-K 保留 | ✅ 确认 |
| 边衰减 GC P2 评估 | ✅ 确认 |
| Top-K 满额策略 | ✅ 已定：确定性淘汰（上文第 3 节） |
| 边类型分立容量 | ✅ 已定：四类分立（上文第 4 节） |
| 后台任务资源隔离 | ✅ 确认，纳入架构设计 |

**一处保留意见**：关于"记忆压缩（P2-19）"我希望补一条约束进规格——**摘要节点必须携带对原始来源的引用链，且原始来源在被摘要覆盖后不参与"独立来源"计数**。否则反思类功能越强，"摘要冒充一手事实"的风险越大，这会从根上腐蚀 provenance 体系。
